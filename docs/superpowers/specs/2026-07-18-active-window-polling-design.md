# アクティブ窓ポーリング設計

日付: 2026-07-18
対象: `index.html`（フロントのみ。サーバ側変更なし）

## 背景 / 課題

現状、シャッター系デバイスの state を 4 秒間隔で永久にポーリングしている
（`startPolling` の `setTimeout` 連鎖）。タブを開きっぱなしにすると enl 実行が
延々と続き、状態確認としてやりすぎ。静止しているシャッターの状態は勝手に
変わらないので、常時ポーリングはほぼ全てが無駄打ちになる。

ライトは既にポーリング対象外（表示時 1 回 + 操作 2 秒後の追いつき取得のみ）で、
本設計の対象外。既存動作を変更しない。

## 方針

「アクティブ窓」の間だけポーリングし、窓の外ではポーリングを完全停止する
（enl 実行ゼロ）。

- `pollUntil` タイムスタンプを持ち、`now < pollUntil` の間だけ 4 秒間隔
  （`POLL_MS` 据え置き）でループが回る。期限切れでループ自体が終了する。
- 窓を延ばすときは `pollUntil = max(pollUntil, now + ms)`（短縮はしない）。
  ループが止まっていれば再起動する。

## トリガーと窓の長さ

| イベント | 動作 |
|---|---|
| ページ表示（初回ロード） | state を 1 回だけ取得。窓は開かない |
| タブ復帰（`visibilitychange` → visible） | 同上、1 回だけ取得 |
| シャッター操作（個別 open/close/stop・一括とも） | 完了後、窓を「今から 2 分」まで延長してループ起動 |
| ポーリング/1 回取得の結果に `opening` / `closing` がある | 窓を「今から 30 秒」まで延長（下記上限あり） |

### 動作中の自動延長と上限

`opening` / `closing`（動作中）が見えている間は 30 秒ずつ延長し続けることで、
シャッターの動作完了（開ききった / 閉まりきった）を確実に拾う。

ただし延長は直近のトリガー（操作 or ページ表示/タブ復帰）から **10 分を上限**
とする。機器が「開いています…」のまま固まった場合に、無限ポーリング（現状と
同じ状態）へ退行するのを防ぐ。上限判定用に直近トリガー時刻を記録する。

表示時の 1 回取得で動作中が見えた場合（家族の別端末が操作中など）も同じ
延長ロジックで追従する。

## エッジケース / エラー処理

- state 取得エラーでは窓を延長しない。表示は現状どおり（「接続なし」等）。
- `busyCount > 0`（操作中）はポーリングをスキップする既存ガードを維持する。
- 一括操作も個別操作と同様に、完了後に 2 分窓を開く。

## 検証

- `cargo test` / `cargo clippy -- -D warnings` が通ること。
- `RUST_LOG=debug cargo run` でページを開きっぱなしにし、初回取得のあと
  enl 実行が止まることをログで確認。
- 操作後、約 2 分間ポーリングが走り、その後止まることを確認。
- 操作直後の動作中（opening/closing）は完了状態まで表示が追従することを確認。
